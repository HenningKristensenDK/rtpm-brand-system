Mobile app design system

390 × 844 · shown at true size
What mobile is for
A deliberate subset, not the desktop app made narrow.
Candidate for locking
On site
Raise a record at the point of observation, photograph it, assign an owner. This is the only creation flow mobile carries.
Between meetings
Clear the personal queue: approve, comment, tick a checklist item, send an update that is already drafted.
Not on mobile
Registers as tables, the risk matrix, portfolio dashboards, bulk edits, and configuration. Offered as a "open on desktop" hand-off, never as a pinched-in table.
Consequence
Navigation is a four-item tab bar, not the eleven-module sidebar. Modules are reached through search and through the queue, not by browsing.
Layout rules
Margins 16pxContent gutter 16. Cards are full-bleed to those margins, radius 14 as on desktop.
Hit targets 48pxMinimum 44, standard 48. Rows are 72–88px because they carry three lines of context.
Type floor 13pxBody 15, labels 13, never below. The desktop 11.5px caption size does not exist on mobile.
One navy anchorHeader navy, tab bar white with a top border — the same rule that stops the desktop L, applied vertically.

Empty & zero-data states

Six causes, six different messages
Empty is not one state
In a governance system, why a list is empty matters more than the fact that it is.
Candidate for locking
Purpose
An empty register can mean nothing has happened, nothing has been recorded, or the viewer is not permitted to see it. Those are three completely different facts about a project, and conflating them is a governance failure, not a UX one.
Design principles
Every empty state names its cause, states what is true, and offers exactly one action — or none. No illustrations, no mascots, no exclamation marks. A striped placeholder block stands in where a chart or table would be, so the layout does not collapse and the reader sees what is missing.
Layout rules
In place, not centredThe message sits inside the container it explains, at its top-left, so surrounding structure stays legible.
Three lines maximumCause heading 15px semibold, one explanatory line 13px, one action. Nothing else.
Colour is earnedNeutral by default. Only "restricted" and "unavailable" take a status colour, because only they are conditions.

Say how many records exist when the view is filtered or restricted. The count is the fact.

Add an illustration, an icon set or encouraging copy. This audience reads it as evasion.
Collapse the container. A missing chart leaves its frame so the absence is visible.

Agent states

Eight states · one gold hairline · no animation
The full state set
Section 06 locked the agent's principles and its two main screens. These are the states in between.
Candidate for locking
Purpose
An agent that cannot say "I don't know", "I'm not allowed to see that" or "this data is old" is not governable. Each state below exists so the agent can be honest about its own limits in a form an auditor would accept.
Design principles
Every state is a header dot plus a sentence. The dot uses the locked status scale — green ready, gold working, red failed, grey inert — and the sentence carries a count or a timestamp wherever one exists. No spinner, no pulsing dots, no shimmer.
Layout rules
State lives in the headerDot and label in the panel header, never floating over the thread. The thread stays a record.
Progress is counted"Reading N of NN records" — a number that changes, not a bar that animates. Cancellable at any point.
Failures stay in the threadA refusal or an error is a message in the thread, not a toast. It is part of the audit record.

Introduce a new colour for AI. The gold hairline is the only marker.

Board view

The Board toggle beside every register Table
Columns are the four workflow stages
Not custom lanes. The board is the register's four-stage rule turned sideways.
Candidate for locking
Purpose
Show where work is stuck. A table answers "what is on the register"; a board answers "what has stopped moving, and in whose hands". It is a working view for a weekly control meeting, not a reporting view.
Design principles
The columns cannot be renamed, reordered or added to — they are the record type's four stages, so a board is directly comparable to its table and to every other module's board. Ageing is the board's headline signal: cards carry days-in-stage, and a column reports how many of its cards are stale.
Layout rules
Four columns, equal widthMinimum 260px each. Column header carries the stage name, the count, and the stale count when above zero.
Card is five factsID, severity, title, owner, days in stage. Nothing else fits and nothing else is needed to decide.
Drag writes an audit lineMoving a card is a state change: it is attributed, timestamped, and can require a reason. Never a silent drag.
Forward only by defaultBackward moves are permitted but prompt for a reason, because a regression is a fact someone will ask about.

✓Do
Show days-in-stage on every card, and turn it red only past the stage's own threshold.

Colour whole cards by severity. The left border and the dot carry it, as in the register.
Keep resolved cards on the board indefinitely — the board is for work in motion.

Operational workflow states

Stage is where · state is how it is going
Two independent axes
The four-stage rule is untouched. These states sit across it, not inside it.
Candidate for locking
Purpose
A record at stage three can be running normally, waiting on a third party, formally on hold, escalated, or superseded. All five look identical on the stepper. Without a second axis the register cannot distinguish work that is progressing from work that has stopped, and the whole control claim fails.
Design principles
Nine states, one visible at a time, chosen by a fixed precedence so two people reading the same record never see a different label. Six use the locked status scale; three are neutral because they are administrative, not conditions. Every non-normal state requires a reason and an owner before it can be applied.

One badge leads, the rest are stated. The reason and the person who applied the leading state appear directly beneath, and the change is written to the audit trail.
Why silence matters
"In progress" shows no badge. On a register of two hundred rows, every badge is an exception — so the eye counts problems, not records. A system that labels everything labels nothing.
✓Do
Require a reason and an owner before any non-normal state can be applied.
Stop the clock on hold, and show that it is stopped rather than showing a stale count.
Link a superseded record forward to its successor, and keep it readable.
Show secondary states as plain outline chips beside the leading badge.
×Don't
Add these to the stepper as extra stages. The four-stage rule is locked.
Show two badges in a register row. One leads, by precedence.
Delete a superseded or closed record. Nothing leaves the ledger.
Label the healthy majority. In progress is the absence of a badge.

Candidate
Coverage. With these ten locked, the Product Design System covers every surface a future module needs: shell, dashboard, register, board, record, mobile, agent, empty states and operational states. A new module is assembled from them — it should not require new patterns.
Three decisions for Henning
01 · Mobile scope
Mobile carries the queue, the record and one raise flow — no registers, no dashboards, no matrix. That is a real limitation. Confirm it, or name the one thing missing from it.
02 · State precedence
Escalated outranks Overdue, which outranks Awaiting external, which outranks On hold. If your buyers read that order differently, this is the moment to reorder it — every view depends on it.
03 · Backward drags
A card can be dragged back a stage if a reason is given. The stricter alternative is to forbid it entirely and require a reopen. Say which your governance story needs.
